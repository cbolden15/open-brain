# W5 P0 transition and recovery contract v1

Status: specification only. Guide writes use existing owner application/engine authorities; collector retains capture-only application capability. No automatic compensation, retry loop or extra authority.

## Transition table

Every write requires its own current intent and confirmation. Persist exact request before entering the authority call. Lost acknowledgement always stops automatic advancement; a later explicit resume may reconcile/replay only the same confirmed request under the rules below. Refusal never proves that a prior write did not commit.

## Scoped policy authoring gap: exact bounded contract

The new owner helper previews the unchanged launcher-policy.v1 document using principal_id=`guide:`+SHA256(UTF8(workflow_id))+`:client` and session_id=`guide:`+the same digest+`:session`. These generated IDs are shown for explicit owner approval; no manual ID copy is required. Set capabilities=[search,content-read], space_ids=[dedicated_destination], allowed_read_tiers=[work], allowed_capture_tiers=[], egress_mode=external_provider, provider_id=chosen single provider, consent_id and authorization_generation from the currently validated DurableProviderConsentStore, brain_id/issuer_epoch from current owner context. All values pass parse_launcher_policy and validate_startup_policy before preview/apply. No wildcard space, owner authority or extra grant.

Preview returns complete canonical policy bytes and SHA ephemerally. The helper apply request is metadata `{policy_path,policy_sha256,expected_absent:true,workflow_id,destination_space_id,provider_id,consent_id,authorization_generation,brain_id,issuer_epoch}`; regenerate proposed bytes from precisely those already confirmed inputs, compare SHA and revalidate current consent/identity before create. File body never enters journal; after crash this halt-only request is not replayed or reconstructed. Existing policy can be used only if a fresh parser/authority read proves exact scope and consent, followed by explicit owner confirmation; no overwrite, generation repair or widening.

## Journal v1

An app-owned file outside Brain and collector stores; parent0700/file0600, owned regular single-link file, no symlinks, atomic fsync+rename and directory fsync. Maximum256KiB. Closed top-level shape:

```text
{schema_version:1,workflow_id:ID,revision:int,status:"active"|"cancelled"|"completed"|"halted",
 binding:{brain_id:ID,issuer_epoch:int,brain_root:string,collector_state:string,
          collector_binding:string,executable:{path:string,sha256:HEX64,device:int,inode:int}},
 choices:{connection_id:ID|null,resource_id:ID|null,resource_type:ID|null,date_floor:string|null,
          account_alias:string|null,destination_space_id:ID|null,client_kind:string|null,
          context_path:string|null,consent_state:string|null,policy_path:string|null,runtime_path:string|null,provider_id:ID|null,scope:string|null,client_version:string|null,launch_context:LaunchContext|null},
 operations:Operation[0..1000],retained_receipt_ids:ID[0..1000]}
Operation={sequence:int,action:Action,intent_sha256:HEX64,request_sha256:HEX64,
 canonical_request_utf8:string,canonical_intent_utf8:string,confirmation:"unconfirmed"|"confirmed",
 state:"prepared"|"executing"|"completed"|"unknown"|"refused",
 executing_pid:int|null,evidence:OperationEvidence|null}
```

`canonical_request_utf8` is the exact normalized non-content public API request, not the CLI decision file and not a reconstruction. canonical_intent_utf8 is the exact canonical confirmation-hash preimage from INTERFACE.md, including ordered expected_versions and execution_binding. Persist it before returning needs_confirmation, preserve its byte/order identity across processes, and validate SHA256 plus correspondence with action/request_sha256/canonical_request_utf8 on every load. Never recreate it from live state or reorder versions. No config/policy/body contents enter this preimage. Native canonicalization/digest rules still apply within each authority service. OperationEvidence is a closed per-action projection: collector `{source_id,preview_id,receipt_ids}`; space `{delivery_id,space_id}`; route `{source_id,head,route_version,operation_id,request_sha256}`; consent `{operation_id,consent_id,request_sha256}`; selection `{selection_id,member_source_ids}`; sharing `{operation_id,preview_id,approval_id,copy_capture_id,state,receipt_sha256}` with unavailable nullable fields; policy `{policy_sha256,path}`; setup `{preview_id,status,changed_path_count}`; observation `{projection_sha256,revision_id}`. Full frozen native request/receipt shapes remain the authority; saved guide evidence must never manufacture a success receipt. Native response fields not needed for reconciliation remain outside journal.

No bodies, tokens, provider answers, credential references, raw errors, config/policy contents or resource inventories. Account alias is a display hint. Journal itself is private metadata, not Portable content. Validate IDs/versions/counts and all unknown keys before use; duplicate keys/nonfinite/deep JSON refuse. Old/future schema, malformed file, binding mismatch or unsafe paths refuse without migration/repair. Older guide binaries must reject unknown journal schema; this does not fence older engine binaries at the same17/12/12 coordinates.

Acquire a nonblocking journal lock only to read/CAS/write its revision; release before child execution/owner prompt/engine lease. Persist executing marker and increment revision before authority entry. A second process seeing executing must return journal_busy; a stale marker is never cleared by elapsed time alone. In addition to the short journal CAS lock, use an operation-lifetime flock guard in the private journal directory, owned0600/no-follow and bound to this workflow. Acquire it nonblocking BEFORE writing executing state or entering any authority operation. Keep this guard (not an engine lease or journal CAS lock) until all potential authority work has stopped. Pass its open-file-description FD to the collector via pass_fds and the additive --guide-guard-fd flag; collector protocol1 must validate the FD and keep it open for its entire operation lifetime. Thus supervisor SIGKILL cannot release the guard while its collector child still runs, including the spawn-before-child-PID-record gap. No child engine/custody mutation may outlive this guarded process; transport-only HTTP workers have no engine authority. Reconcile must acquire the SAME existing guard nonblocking before reserving a new journal revision; busy/unsafe/unverifiable guard means halt. Never unlink/replace a busy guard file or steal it by PID, elapsed time or owner checkbox. executing_pid is diagnostic only, never liveness proof. A worker writes its result only with the reserved revision. Journal CAS lock is released before child execution; the lifetime guard is released only after child reap or proven no remaining authority process. A guard without a valid journal is unavailable, never repaired automatically. No background recovery. Different journals rely on engine/collector CAS, not this lock. At most one outstanding authority operation per journal.

Journal writes require bounded preflight capacity reservation for request plus maximal retained response; if it cannot fit, refuse BEFORE authority call. Do not prune unresolved/confirmed evidence to fit. Completed journal is retained until explicit owner removal; no TTL deletion. Removal is an owner file operation after processes stop, with warning that receipts/captures/releases persist and safe resume evidence is lost. Continuation may create a new journal only after all outstanding operations resolved/halted and fresh authority inspection; it does not clear custody quota. No guide maintenance daemon.
